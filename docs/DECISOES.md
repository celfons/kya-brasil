# Decisions

| # | Decision | Reason |
| --- | --- | --- |
| D-01 | Repository and Worker separate from KYB Brasil; code may be duplicated. | Different products, separated responsibility. KYB does not know KYA exists. |
| D-02 | KYB called via Service Binding (`KYB`) on the `/internal/v1/*` channel with `KYB_INTERNAL_KEY`. | Worker-to-Worker call with no public HTTP and no x402; the credential price already covers the lookup. Locally: `KYB_URL`. |
| D-03 | Binding proof in phase 1 = e-CNPJ (ICP-Brasil), detached CMS/PKCS#7 over the challenge text. gov.br in phase 2. | Every company has an e-CNPJ; the signature proves possession with no intermediary. |
| D-04 | Agent keys: EVM wallet (EIP-191) and Web Bot Auth (Ed25519, RFC 9421). | Covers agents that pay with x402 and HTTP agents that sign requests. |
| D-05 | Mandate = free-form JSON validated by a public schema; only the reserved fields are evaluated in `/allowed`; the others are listed in `not_evaluated`. | Flexible without promising what is not checked. |
| D-06 | Credential signed with Ed25519 (same attestation scheme as KYB), retired keys published in `/.well-known/kya.json`. | Offline verification, stable after rotation. |
| D-07 | Verification free up to 50/day per IP; `/verified` and `/allowed` at 0.01 with no limit; registration 0.50 (current price 0.25: see D-22); renewal 0.10; proof and revocation free. | Verifying must be cheap for the verifier; the issuing side pays. |
| D-08 | Without ICP-Brasil anchors in KV, no issuance (fail closed). | An unvalidated chain would be a fake credential with a real signature. |
| D-09 | Daily review by cron: suspends those that no longer pass KYB, reinstates those that pass again. The signature covers the credential as issued; the live state is in `verify_url` and `/v1/revocations`. | Avoids re-signing on every change and keeps the history auditable. |
| D-10 | No CPF stored or exposed; the e-CNPJ signer is recorded only by the certificate hash. | Same rule as KYB Brasil. |
| D-11 | ERC-8004 only in phase 2. | First prove demand with an off-chain credential. |
| D-12 | Phase 2, ERC-8004 read-only: the agent registered on-chain is identified by `eip155:<chain>:<registry>:<agentId>` and signs with the `agentWallet` read on-chain; nothing is written on-chain. | No gas cost or operational wallet; the credential stays off-chain and verifiable. Writing (on-chain validations) waits until there is demand. |
| D-13 | gov.br proof removed from the roadmap. | The technical guide for Login Único (Portaria SGD/MGI 7.076, art. 3º) only grants production credentials to systems hosted on an official government domain; the integration service is for public services, case by case. A private issuer does not qualify. The e-CNPJ already covers the legal entity with its own legal validity (MP 2.200-2); ERC-8004 covers on-chain identity. |
| D-14 | *(Revised by D-19.)* Act log: whoever accepts the action records it (0.02); the issuer re-evaluates the mandate by adding what was already recorded that day; signed receipt; denied acts are kept as proof and do not count toward the total; full trail only for the company, signed with e-CNPJ; only the document hash. | Closes the self-declared daily limit and gives after-the-fact proof without storing content. The counterparty is the one with an interest in recording. |
| D-15 | KYA scope = the agent–company binding and its validity. Issuance and status depend only on (a) a valid, unrevoked e-CNPJ certificate and (b) the company being ATIVA at the Receita Federal. Sanctions, the slave-labor "dirty list", debt, embargoes and risk scores do not deny or suspend a credential. `kyb_snapshot` stays in the v1 credential for information only (/v1 rule: fields are not removed); it goes away in a v2. The daily review uses only the registration status from KYB (`br_company_check`); suspensions made under the old rules are lifted in the review if the company is ATIVA. | Identity is fact; risk is the policy of whoever accepts the request. An issuer that denies identity based on a score mixes the two, loses neutrality and is wrong when the score is wrong. KYB stays available to the verifier, with the CNPJ that the credential provides. A closed-down company has no one to answer for the agent: that is about the binding's validity, not risk. |
| D-16 | e-CNPJ revocation via the CA's CRL: at issuance, at renewal and when reading the act trail, a listed certificate is refused and so is an unavailable CRL (fail closed, as in D-08). In the daily review: listed → credential revoked; `certificateHold` → suspended until it leaves the list; `superseded`/`cessationOfOperation` after the authorization → nothing (replacement without compromise). An unreachable CRL in the review changes nothing that day. Stored: serial number, issuing CA certificate and CRL URLs (public data, no CPF). CRL cached in KV until nextUpdate (max. 6 h). OCSP is not used. Credentials older than this decision lack this data and are only checked at renewal. | With the scope of D-15, certificate revocation is the issuer's core responsibility; before, a stolen and revoked e-CNPJ kept authorizing for up to 90 days. ICP-Brasil requires a CRL from every CA (DOC-ICP-04); OCSP is optional. Revoking on a normal certificate replacement would punish the company for no reason. |
| D-17 | Configurable source for registration status (`REGISTRATION_SOURCE`: `auto`, `kyb`, `public`). `auto` (default) uses KYB when there is a `KYB_INTERNAL_KEY` and a binding/URL; otherwise the Receita open data via BrasilAPI, with CNPJ.ws as fallback. Without KYB the credential's `kyb_snapshot` is `null`. Infra and CD treat KYB as optional (no key, no binding). Production stays on `auto` with KYB. | After D-15 the issuer only needs one piece of public data; requiring a closed service kept any fork from running. The Receita has no free API per CNPJ (lookup with CAPTCHA); BrasilAPI and CNPJ.ws serve its open data. |
| D-19 | Act log removed (revises D-14): routes, MCP tools, SDK and the `acts` table (migration `0005`) are removed. `max_per_day` is again evaluated with the `spent_today` supplied by the caller; `/allowed` keeps `spent_today_registered: null` for /v1 compatibility. The PR for proof of the act's origin (proposed D-18) was closed without merging. | KYA answers who speaks for whom and with what mandate; what the agent did is recorded by whoever received the request, in their own system. In production no act had been recorded; keeping the trail cost schema, pricing, privacy and a responsibility (witnessing the act) that pulled the issuer outside the scope of D-15. |
| D-20 | The company sees and hears its agents: inventory (`POST /v1/companies/{cnpj}/agents`) and a webhook of signed credential lifecycle events (issued, renewed, suspended, reinstated, revoked; nothing about what the agent does or requests, consistent with D-19), both free and authorized by text signed with e-CNPJ with `at:` of up to 10 min; the webhook only accepts a request newer than the last one, https on a host name. Best-effort delivery (one attempt, 5 s). | Without this, a credential issued by someone who had the certificate (accountant, former employee) acted on behalf of the company without it knowing; the leaked key only showed up later. The e-CNPJ is the proof that whoever is asking is the company. |
| D-21 | Explicit availability: `/status` shows the result of the last daily review; the SDK has `verifyCredentialOffline`, which checks signature and validity and returns `live_status: "unknown"`; the terms say that, with the issuer down, accepting only the offline check is the verifier's risk until `expires_at`. No SLA. | Live status depends on the issuer. Instead of promising what does not exist, the verifier knows what the offline check proves (what was issued) and what it does not prove (later revocation). |
| D-22 | Registration at 0.25 (revises D-07; renewal stays 0.10, verifications 0.01). | Registration is paid by the company that owns the agent, the side that needs convincing; 0.25 every 90 days removes the price objection without changing the model. The marginal cost of issuance is one registry lookup and one CRL. |
| D-23 | No dependency on KYB Brasil (revises D-01, D-02 and D-17): the `kyb.ts` client, the `KYB` Service Binding, `KYB_INTERNAL_KEY`, `KYB_URL` and `REGISTRATION_SOURCE` are removed. Registration status comes from the Receita open data: `CNPJ_API_URL` (optional, BrasilAPI format, tried first), BrasilAPI, CNPJ.ws. `/status` shows `registration_sources`. For /v1 compatibility, `kyb_snapshot` (always `null`), `kyb_warnings` (always empty), the `KYB_BLOCKED` error code (company not ATIVA) and the `last_kyb_at` column remain. | An open project should not depend on a closed service or be coupled to another product: after D-15 the issuer only uses public data. BrasilAPI and CNPJ.ws are free, keyless mirrors of the open data; anyone who does not want to depend on any third party points `CNPJ_API_URL` to their own database. |
| D-24 | The registration status check is optional and never takes the service down. Verifications (`/verified`, `/allowed`, free lookup) never call it. At issuance and renewal, only a confirmed status other than ATIVA refuses; a source that is down becomes `UNVERIFIED` and `REGISTRATION_CHECK=off` becomes `NOT_CHECKED`, both with a warning in `warnings` (repeated in `kyb_warnings`) and the company name taken from the e-CNPJ certificate. In the daily review, an unknown status changes nothing (no suspension or reinstatement). `/status` shows `registration_check`. | A third-party public source being down must not stop a company from getting a credential already proven by the e-CNPJ, which is the central proof. The credential tells the truth (`UNVERIFIED`) and the verifier decides whether to require `ATIVA`; the daily review confirms later. |
| D-25 | (a) Mandate with `payment_instruments`: list of `{ network, ref_sha256, label? }`, where `ref_sha256` is the SHA-256 of a reference the payment network already provides (network token, PAR), never the card number; values that are not a 64-hex hash and labels with 12 or more consecutive digits are refused. `/allowed` and `kya_check_action` accept `payment_network` and `payment_ref_sha256`; the signed verdict repeats both. (b) `packages/core` published as the `@kya-brasil/core` library (formerly private `@kya-br/core`): the same issuer functions, pure, to verify or issue without the hosted service. | Card networks, acquirers and issuers need to link the payment instrument used in the transaction to a company that authorized the agent, and keep proof of it for disputes. A hash of the network's own reference keeps KYA out of PCI scope. Institutions of that size do not depend on a small third-party service: they import the logic, run it with their own keys and audit, and the hosted service becomes the reference implementation. |
| D-26 | e-CNPJ signing without code: a `/sign` page (`sign_url` link returned at registration; the agent appends `&agent_signature=`) that shows CNPJ, agent, issuer, validity and requested mandate, warns if the challenge is from another issuer or has expired, and signs in the browser with the `.pfx` (node-forge with pinned SRI, strict CSP, no referrer; file and password never leave the browser) or accepts a `.p7s` from any ICP-Brasil signer over the challenge file (A3, cloud). On npm: `signWithECnpjPfx`, `signingLink` and the `kya-sign` command. Attached CMS accepted only if the content is exactly the challenge. A pending registration shows `requested_mandate`. Recommendation: the agent prepares and sends the link, a person signs; the agent should not keep the company's certificate. | Signing CMS outside the usual programs was the biggest friction for the company, and the one who holds the certificate is often the accountant. A link that shows what is being authorized and signs with what the person already has (A1 file or the token's signer) removes the friction without taking the decision away from a person: the e-CNPJ signature is the company's consent. |
| D-27 | Signature by the e-CNPJ holder in `@kya-brasil/core`: `buildDetachedCms` builds the CMS from the chain and a function that signs bytes (RSA PKCS#1 v1.5 SHA-256), serving A1 (`openPfx`), A3 token, HSM and cloud certificate (`ecnpjSigner`); `signingLink`/`readSigningLink`. In `@kya-brasil/agent-tools`: `openToken` / `listTokenCertificates` (PKCS#11 via `pkcs11js`, optional dependency) and `kya-sign --pkcs11`; the client now depends on core and re-exports the signing functions. On the server: `kya_sign_link` (MCP) and `GET /v1/agents/{id}/sign-link`, free, with the same `signingLink` as core. The `/sign` page keeps signing in the browser with node-forge (same steps). Tested with SoftHSM2 in CI. | A1 and A3 need the same path in code, terminal and browser, without depending on the page or a route: integrators (platform, bank, acquirer) sign with their own token or HSM using the library, and the agent requests the link through the same interface (MCP or HTTP) it already uses. x402 billing stays only on the server; core has no payment. |
| D-28 | Cloud e-CNPJ certificate through an interface, with no PSC implementation in the project: `CloudSignatureProvider` (`authorizationUrl` with PKCE S256 and `state`; `exchangeCode` returning a session with `certificates()` and `signHash(sha256)`), `cloudSigner`, `pkcePair`, `newState` in core. Three entry points: library; `kya-sign --cloud <module>` (browser to approve, single callback on 127.0.0.1); the `/sign` page of your own issuer (`/sign/cloud/{provider}/start` and `/sign/cloud/callback`, single-use state in KV for 10 min, PSC session only during the callback, signs only the stored challenge). The reference issuer configures no provider. Template in `examples/cloud-provider`. | Each PSC has its own contract, registration and details; implementing providers in the open project would create dependency and maintenance that are not the project's. The interface lets whoever has a contract plug in theirs, and KYA guarantees what matters for security: PKCE, single-use state, what is signed and the CMS assembly. |
| D-29 | Agent of an individual with e-CPF (revises D-10 for individuals only). Stored: only `HMAC-SHA256(versioned secret key, CPF)` and the version, while the credential is valid; never the name, plain CPF, masked CPF or certificate subject. Public credential: `principal: { kind: "person", verified_by: "icp-brasil-e-cpf" }`, with nothing personal. Paid lookup (0.01) `POST /v1/agents/{id}/principal-match` with the CPF the verifier already has: answers only whether it matches, signed, and on a match a `subject_ref` specific to that verifier (different for each one, so services cannot be cross-linked); 3 negative answers per credential and verifier block further lookups; the CPF in the lookup is not stored. Consent in the text signed with the e-CPF itself. The person sees their credentials and all lookups (`POST /v1/people/agents`, signed with e-CPF), with no active notice. Revocation with the same e-CPF. Hash and lookup log deleted on revocation or expiry. Daily review of the CRL only. Without the key configured the issuer refuses (fail closed). | People will also delegate to agents, and whoever receives the request wants to know there is a real, identified person, without KYA becoming a CPF database. An unkeyed hash would be reversed in minutes (CPF has ~10^9 values) and a masked CPF would cut the search to ~a thousand; hence only HMAC with a secret key. The paid, limited lookup prevents using the issuer as a CPF oracle, and the per-verifier identifier gives the recipient the control it needs without allowing tracking across services. |
| D-30 | Delegation to subagents without a new certificate signature. The holder allows it in the mandate they sign (`delegation: { max_depth 1..3, max_ttl_seconds 60..86400 }`; absent = no delegation). The agent signs with its own key a short delegation that gives another key (`evm` or `web-bot-auth`) a mandate **contained** in its own; the delegate may delegate again while depth allows. The chain travels in the `KYA-Delegation` header, the request text gains a `delegation:` line with the header's hash and the signer is the last delegate. Offline verification (`verifyDelegationChain` in core, middleware in agent-tools); the action is allowed only if **all** mandates in the chain allow it. The issuer stores no delegations, has no new route, and `/allowed` still evaluates only the credential's mandate. No revocation of its own: short validity, and revoking the credential takes down the chain. Along with this, core's `checkAction` now accepts `*.` in `counterparties`, as §5 already said. | Agent systems create subagents, some short-lived; requiring an e-CNPJ or e-CPF for each one is the friction of D-26 multiplied, and the practical way out would be sharing the agent's key, which is worse. One holder signature covers the tree, within the limits they wrote. No state in the issuer keeps it consistent with D-19 (it does not record what agents do) and D-15 (the holder is still the one who answers). Accepted cost: the company's inventory does not show subagents; whoever receives the request sees the whole chain. |
| D-31 | Local MCP server `@kya-brasil/mcp` (stdio), in addition to the remote one in the Worker. Offline tools with core (evaluate an action against a mandate, validate a mandate, verify a delegation chain, check a credential signature), the issuer's free ones through the public API (`kya_verify`, revocations, signing link) and the paid ones (`kya_check_action`, `kya_verify_paid`) via x402 when `KYA_PRIVATE_KEY` exists; without a key it starts the same way and the paid ones answer `PAYMENT_REQUIRED`. Published as a single bundled file (esbuild), with no runtime dependencies. CI bundles and starts the server over stdio on every push. | Directories such as Glama only evaluate and list servers that build and run in their own container, with no bridge to an external address; the Worker's MCP depends on Durable Objects, D1 and x402. For Claude Desktop or Cursor users, a local server also makes verification truly offline and does not require trusting the hosted service's transport. Registration and proof stay out: they need the certificate signature and go through `/sign`, `kya-sign` and the library. |
| D-32 | Status freshness proportional to value, decided by the verifier. Core gains `freshnessPolicy`, `maxStatusAgeSeconds`, `checkFreshness`, `checkFreshAction`, `evidenceFromRevocation` and `evidenceFromSignedStatus` (SPEC §18). The verifier declares the expected loss it accepts per action (*L*) and the revocation rate it assumes (*λ*, per kind: credential and certificate); the maximum age of the status proof is *L / (v × λ)*, with a ceiling (default 1 day) and clock tolerance (default 300 s), or a custom function. Fail closed: no proof, different currency, invalid value or invalid clock means refusal. The verdict records the policy and clock applied and says which proofs need to be renewed. The credential proof can be any issuer-signed response with `credential_id` and `status`, which the agent can attach to the request. No network in core and no change in the issuer. *λ* has no default. Applies to any action, not only payments: without a monetary value, the verifier assigns a risk value per action name (`action_risk_value`); with neither, the ceiling applies. The mandate's daily ceiling limits the damage of a stolen key within the window, but counting spending, applying a stricter ceiling of one's own or limiting the number of actions per day is the verifier's decision and risk: core keeps no state. No business defaults in the library: every value that expresses a risk decision (tolerated loss, rates, ceiling, clock tolerance, required proof kinds, unknown-value action, expired proof, the clock itself) is mandatory and comes from the user; core only validates the format. This includes whether to accept a CRL after `nextUpdate` (`pastNextUpdate` in `verifyCrl`/`checkRevocation`, `past_valid_until` in the policy), which Li and Feigenbaum (FC 2001) argue should be judged by age; the reference issuer passes `"refuse"`. | Without network access, SPEC §8 left the risk of a revoked credential "with the verifier, until `expires_at`" (up to 90 days) with no way to express it. Always checking synchronously adds latency and an availability dependency and does not remove the window (the ICP-Brasil CRL comes out at intervals of hours); leaving it without a rule repeats the browsers, which gave up checking. Whoever accepts the action is the one who bears the risk, so they set the requirement (Rivest, 1998), and the requirement grows with the value. *λ* has no default because it had not yet been measured; an invented default would become the value everyone uses. |
| D-33 | The certificate signs the mandate. The challenge text (company and individual) gains a `mandate-sha256:` line with the SHA-256 of the canonical JSON of the mandate stored with the challenge; the issuer refuses to issue if the signed text does not carry the hash of the mandate it is about to issue; the credential records the hash in `authorized_by.mandate_sha256`, and any verifier checks it offline (`verifyMandateAuthorization`: `signed`, `mismatch`, `not_covered`). The `/sign` page computes the same hash in the browser, warns if it does not match the mandate shown and offers to download the signed text and the `.p7s`. The issuer does not store the CMS. | Until now the ICP-Brasil signature covered only the binding (this key acts for this CNPJ or CPF); the powers were shown to the holder and attested by the issuer. Under the Civil Code, a power of attorney is valid with the grantor's signature and must state the extent of the powers (art. 654), and the presumption of truth of MP 2.200-2 (art. 10, § 1º) only reaches what was signed: without the hash, the powers fell outside it. The CMS stays with the holder because it carries the signer's certificate, with the name and CPF of an individual, which the issuer neither stores nor returns (D-29, CONTRIBUTING). Earlier credentials remain valid as `not_covered`. |
| D-34 | Verification without trusting the issuer. The agent can present, with the request, the text the holder signed and the `.p7s` (`KYA-Principal-Proof` header), and the verifier checks it alone, with the ICP-Brasil anchors: signature and chain, same certificate the credential records, agent, CNPJ or individual, issuer and mandate hash (`verifyPrincipalProof`, SPEC §19). Certificate revocation is left to the verifier, through the CRL. Result with no personal data. | Even with D-33, the verifier depended on the issuer's key to know the credential was authorized: a compromised or dishonest issuer could sign a credential the holder never authorized. With the holder's own proof, the issuer is only responsible for the credential's status after issuance. The cost is privacy: the CMS carries the signer's certificate, so the holder decides when to hand it over, as they would with a power of attorney, and the verifier treats it as personal data. |
| D-35 | Credential lifetime is a mandatory parameter and never exceeds the certificate. Core no longer has `CREDENTIAL_TTL_DAYS` (fixed 90 days): `buildCredential` and `buildPersonCredential` require `ttl_seconds` and `certificate.not_after`, and `credentialExpiry` returns the earliest of now + lifetime, `mandate.valid_until` and the certificate's end of validity; an already expired certificate, and a lifetime that is missing, zero, negative or not finite, are refused. The reference issuer keeps 90 days as its own choice. | The lifetime is the issuer's risk decision, and the library carries no business rules (D-32). Without the certificate limit, a credential could stay active with the e-CNPJ or e-CPF expired, and the proof verified only against ICP-Brasil (D-34) would fail before the credential did. |
| D-36 | The effect of certificate revocation on what it already authorized is the relying party's policy. `revocationEffect` now requires a `CertificateRevocationPolicy`: for each RFC 5280 reason, revoke, suspend or keep; for the others, including an entry with no reason, revoke or suspend (never keep). Two rules always apply, because they concern the signature and not the mandate: an authorization signed with an already revoked certificate is not kept, nor when the `invalidityDate` reported by the CA (suspected compromise) is not later than it; without the authorization date, "keep" becomes "revoke". The CRL now exposes `invalidity_date`. The reference issuer keeps the D-16 rule as its own policy. | Revoking the certificate is not a cause for ending a mandate under the Civil Code (art. 682: revocation, renunciation, death, legal incapacity, change of status, term); a normal certificate replacement should not take down powers already granted. Key compromise, on the other hand, affects the signature itself, and the presumption of MP 2.200-2 (art. 10) only covers a valid certificate. ICP-Brasil requires revocation for faulty issuance, data change, CA dissolution or compromise (DOC-ICP-05, 4.9.1.2), and different reasons call for different effects. The one who decides is the one who bears the risk, as in D-32. |
| D-37 | Issuance by the responsible party, with no intermediary issuing service. The format of the binding between ICP-Brasil and the agent belongs to KYA, so core also issues: `buildMandate` (all risk fields mandatory: non-empty actions, per-operation and daily ceilings, currencies, counterparties, payment instruments, validity and `delegation` or `null`; `[]` means "any"; absent is an error), `mandateSigningInput` (the same challenge text that `verifyPrincipalProof` reads, with the SHA-256 of the mandate's canonical JSON), `assembleCredential` (checks the CMS, the chain and the CNPJ as the verifier will and refuses what it would refuse), `buildDelegation` / `assembleDelegation` (the parent agent is the issuer of the subagent's mandate; refuses power amplification and disallowed delegation) and `verifySelfIssuedCredential`. The credential has `issuer: "urn:kya-brasil:self"`, with no Ed25519 attestation: the holder's signature is the proof; the status is that of the certificate (CRL) and the credential's own lifetime. Core does not talk to an A3 token (PKCS#11, PIN): the signature comes in as a parameter, from any ICP-Brasil signer (`openPfx`, `ecnpjSigner`, `cloudSigner`, `openToken` from `agent-tools`). The Alloy model gains the delegation permission (`deleg`) and `issuable`, with three assertions with no counterexample, and the conformance vectors go from 1,020 to 1,320. SPEC §20. | Without anyone to issue, the verifier checks a format nobody knows how to produce; an issuing service in the middle would be one more third party to trust, and verification without an issuer (D-34) already removes that third party. Issuing with the same functions as verification keeps the two from diverging. With no service there is no revocation of a single credential: hence short lifetimes, and whoever needs that uses an issuer. |
| D-38 | A signed request is valid for at most 600 s, and its `created` may be at most 300 s in the future (SPEC section 14); the replay memory keeps each accepted request until its own `expires`. | Same problem as Kerberos: replay detection between clocks that are never exactly in sync, with a typical tolerance of 5 minutes (RFC 4120, section 1.6). The lifetime is twice that tolerance, so a clock ahead or behind still fits. Keeping each request until it expires is DPoP's rule for proofs (RFC 9449, section 11.1); with that memory, the lifetime bounds storage, not security (Alloy: `NoReplayImplemented`). |
| D-39 | Delegation depth is at most 3 levels. | Same depth as the ICP-Brasil hierarchy (AC Raiz, first-level and second-level ACs before the end-entity certificate), and exactly what the Alloy model checks exhaustively: chains up to 4 mandates, the signed one plus 3 delegations (`ChainNonAmplification`, `IssuedChainNonAmplification`). A deeper chain would leave the verified scope. |
| D-40 | Ed521 CRLs (AC Raiz v7, OID 1.3.6.1.4.1.44588.2.1) are refused as unsupported: revocation unavailable, fail closed. | The core verifies CRL signatures only with Web Crypto, which has no Ed521; the algorithm has no IETF specification or official test vectors; and the only implementation found refuses AC Raiz v7's real signatures. Reading the whole SHAKE256 output, as RFC 8032 does for Ed448, makes them verify (`research/crl-compat/go-e521`), but that form was inferred from two signatures. End-user CRLs, which e-CNPJ and e-CPF verification needs, are RSA and unaffected. Support waits for a specification or ITI confirmation. |
| D-41 | The freshness simulation takes the value and the rate of actions from the two means of payment agents reach most easily, Pix and credit card, each from the Central Bank's open data: Pix between companies of different owners (value) and Pix paid per paying company per hour (rate); company credit cards, Empresarial and Corporativo (value and use per active card). The rates are human baselines, so an agent 10 and 100 times as active is a variation. | No public data exists on what agents buy or how often. Hand-picked values (the former R$ 200 median and 2 actions per hour) were the weakest part of the evaluation; the open data replaces them and the variations cover the unknown agent rate. |
| D-42 | The canonical JSON is RFC 8785 (JCS), named as such in the SPEC, with the RFC's own samples in the test suite. What is not JSON data (a number that is not finite, a lone surrogate, a type JSON lacks) is refused. One implementation, in the core; the client imports it. | The hash the certificate signs must come out the same in any language. The code already produced RFC 8785 bytes for every valid mandate, so no hash changes; the SPEC only said "keys sorted, numbers as JavaScript prints them", which another implementer could read differently. Refusing instead of serializing `NaN` as `null` follows the RFC and the fail-closed rule. |
| D-43 | A company mandate may be signed by a legal representative's e-CPF alone (`authorized_by.method: icp-brasil-e-cpf-representative`, text with the line `signed-by: legal representative (e-CPF)`). It is accepted only against the verifier's own list of representatives; with no list it is refused. The e-CNPJ form stays for as long as that certificate exists. | Resolução CG ICP-Brasil 211/2024: from 3 March 2029 a legal person has no signature certificate, only a seal.
